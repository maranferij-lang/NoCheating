# NoCheating — план реалізації системи онлайн-прокторингу для українських ЗВО

> Статус: brainstorm / архітектурний план. Код не пишеться. Репозиторій порожній.
> Мова документа: українська. Дата: 2026-10-03.

---

## 0. Контекст

Українські університети масово проводять навчання і контроль знань онлайн (війна, повітряні тривоги, блекаути, релокація студентів). Виникає проблема академічної доброчесності під час дистанційних тестів і заліків. Ідея: веб-застосунок, який за згодою студента:

1. верифікує особу (обличчя + студентський / ID-картка),
2. сканує кімнату з телефона,
3. під час тесту записує камеру і аналізує погляд / положення голови,
4. формує "підозри на списування" для перегляду викладачем.

Цей документ: чесна оцінка ідеї, продуктова модель, архітектура, технології, оцінка потужностей, правові обмеження, ризики, покроковий роадмап і відкриті рішення.

## 1. Чесна оцінка ідеї (TL;DR)

**Ідея життєздатна, але з двома критичними корекціями.**

| Що пропонується | Оцінка | Корекція |
|---|---|---|
| Верифікація обличчя + документ | Сильно. Стандарт індустрії. В Україні є унікальна перевага: **Дія** (цифровий студентський квиток, паспорт) | Використати Дія.Шеринг / Дія.Підпис як головний шлях, OCR + face match як fallback |
| Сканування кімнати з телефона | **Юридично токсично.** У США суд визнав room scan неконституційним (Ogletree v. Cleveland State, 2022). В ЄС Proctorio неодноразово оскаржували за GDPR. Студенти ненавидять цю фічу найбільше | Зробити **опціональною політикою ЗВО**, вимкненою за замовчуванням. Для МВП не робити |
| Трекінг очей як детектор списування | **Слабкий сигнал сам по собі.** Вебкамерний gaze має точність ~4° при ідеальних умовах, деградує при окулярах, поганому світлі, слабкій камері. Нейровідмінні студенти, люди з ністагмом, звичка дивитись у стелю при роздумах → хибні спрацювання | Gaze = **один з 8-10 сигналів**, що агрегуються у "рівень підозри". Система **не виносить вердикт**, а готує докази для людини |
| "Часто дивиться у конкретний кут" | Це найкраща частина gaze-ідеї. Кластеризація напрямків погляду в часі справді відділяє "задумався" від "читає шпаргалку збоку" | Реалізувати як кластеризацію off-screen fixations (DBSCAN) + dwell time + кореляція з паузами у введенні |

**Ключовий зсув у позиціонуванні:** не "AI, що ловить списувальників", а **"інструмент, що робить дистанційний іспит юридично захищеним і дає викладачу докази для рішення"**. Автоматичні вердикти = скандали, апеляції, судові позови. Human-in-the-loop = продукт, який ЗВО реально купить.

## 2. Хто користувач і що купує

### Ролі

| Роль | Що робить | Що для них важливо |
|---|---|---|
| **Студент** | Проходить онбординг, верифікацію, іспит | Не принизливо, працює на слабкому ноуті, не вилітає при блекауті, зрозуміло, що саме записується |
| **Викладач / проктор** | Створює іспит, задає політику суворості, переглядає флаги, приймає рішення | 300 студентів → не хочу дивитись 450 годин відео. Хочу 15 хвилин на групу: таймлайн із кліпами підозр |
| **Адміністратор ЗВО** | Підключає Moodle, керує політиками, відповідає за персональні дані | Відповідність закону, data residency, звіти, інтеграція з існуючим LMS |
| **Апеляційна комісія** | Розглядає оскарження | Повний запис, незмінність доказів (hash, timestamps), прозорість сигналів |

### Модель постачання

- **B2B SaaS для ЗВО**, оплата за іспито-студента або за річну ліцензію на факультет.
- **Обов'язково інтеграція з Moodle** (де-факто стандарт в українських ЗВО: ВНУ, ЧНУ, МНУ, КРОК, Альфреда Нобеля...). Без цього продукт не продається: ніхто не буде переносити тести.
- Пізніше: Google Classroom, Canvas, власний тестовий модуль.

## 3. Продуктові флоу

### 3.1 Онбординг студента (один раз на семестр)
1. Перехід з Moodle (LTI 1.3 deep link) → екран згоди: **що саме записується, скільки зберігається, хто бачить, як оскаржити**. Згода окремо на біометрію (окремий чекбокс).
2. Перевірка пристрою: камера, мікрофон, браузер, швидкість мережі, CPU-бенчмарк (чи потягне on-device ML).
3. Еталонне фото обличчя (3 кадри + liveness: повернути голову, моргнути).
4. Верифікація особи, два шляхи:
   - **A (основний):** Дія.Шеринг → студент підтверджує в Дії передачу копії студентського квитка / паспорта. Отримуємо верифіковані ПІБ + фото з документа. Face match з еталоном.
   - **B (fallback):** фото документа на камеру → OCR (ПІБ, номер) → ручна перевірка проктором або face match з фото на документі.
5. Калібрування gaze: 9-точкова сітка (дивитись на точки 2-3 сек). Зберігаємо персональну модель.

### 3.2 Перед іспитом (5 хв)
1. Повторний face match (анти-підміна).
2. Перевірка: один монітор (`window.getScreenDetails()` / порівняння `screen` vs `window`), fullscreen, заборонені розширення (евристика), віртуальна камера (евристика за назвою пристрою `MediaDeviceInfo.label`: OBS, ManyCam, Snap Camera).
3. **Опційно (за політикою ЗВО):** room scan — 20 сек відео з телефона через QR-код → другий WebRTC-потік. У МВП не реалізуємо.
4. Опційно: телефон як друга камера збоку/ззаду (стоїть на столі весь іспит). Це дає більше за room scan і менш інвазивно, бо дивиться на стіл і екран, а не на кімнату. Серйозна конкурентна перевага, бо мало хто це робить добре.

### 3.3 Під час іспиту
- Студент проходить тест **у Moodle** (ми не замінюємо тестовий движок). Наш клієнт працює у вкладці-компаньоні або як оверлей через LTI iframe.
- У браузері студента: захоплення відео, on-device ML (обличчя, голова, погляд, об'єкти), запис подій, chunked upload.
- Події браузера: втрата фокусу, вихід з fullscreen, перемикання вкладок, copy/paste, зміна розміру вікна, підключення пристроїв, мережа впала/піднялась.
- Аудіо: тільки VAD (voice activity detection) + рівень гучності. **Не записуємо аудіо за замовчуванням** (окремий чекбокс згоди). Якщо записуємо, то лише фрагменти навколо подій.
- **Блекаут / тривога:** студент натискає "Пауза (тривога)" → проктор отримує сповіщення, таймер тесту в Moodle ставиться на паузу (через веб-сервіс Moodle, якщо ЗВО дозволяє), запис маркується. Якщо з'єднання зникло без паузи, клієнт буферизує події локально (IndexedDB) і дозаливає після реконекту. Втрата зв'язку **не є флагом** сама по собі, а маркером "період без спостереження".

### 3.4 Після іспиту (проктор)
- Список студентів, відсортований за рівнем підозри (0-100) з розбивкою за сигналами.
- Для кожного: таймлайн 90 хв з маркерами; клік на маркер → 10-сек кліп до/після; теплокарта погляду; графік "кількість облич"; лог браузерних подій.
- Кнопки: "Норма", "Попередити", "Порушення (з коментарем)", "Відправити на апеляцію".
- Експорт PDF-протоколу з хешами відео (докази для апеляційної комісії).
- Зворотний зв'язок проктора ("це не порушення") → датасет для калібрування порогів.

### Ключове архітектурне рішення: ML на клієнті (edge-first)

**Чому:** 300 студентів × 90 хв = 450 годин відео за один іспит. Аналізувати це на сервері в реальному часі = GPU-ферма і великі гроші. Натомість:
- **На клієнті (realtime):** MediaPipe Face Landmarker (478 точок, 52 blendshapes, матриця повороту голови) ~15-30 fps на середньому ноуті через WASM+WebGL. Легкий object detector (YOLOv8n / EfficientDet-Lite0 через ONNX Runtime Web) 1 fps. Генеруємо **події**, не стрім сирих даних.
- **На сервері (batch, post-hoc):** лише перевірка флагів важчими моделями на вибраних фрагментах, face match, агрегація.
- **Відео записується** стиснуто (640×360, 10-15 fps, VP9 ~300-400 kbps) і лежить як доказ, але не аналізується кадр за кадром на сервері, крім підозрілих вікон.

Це знижує серверні витрати на 1-2 порядки і дозволяє працювати на дешевих VPS.

**Трейдофф:** слабкі ноутбуки (Celeron, 4 GB RAM) не потягнуть. Потрібен **graceful degradation**: пре-тест бенчмарк → якщо слабкий пристрій, знижуємо fps аналізу до 3-5, вимикаємо object detection на клієнті, компенсуємо серверним аналізом для цього студента.

## 5. Модулі детально

### 5.1 Ідентифікація

| Компонент | Технологія | Нотатки |
|---|---|---|
| Дія.Шеринг | REST API integration.diia.gov.ua, тестовий токен → договір → прод | Безкоштовно для бізнесу, але договір і демо на тестовому середовищі. Треба статус юрособи. Студентський квиток є в Дії як документ |
| Face detection + embedding | InsightFace (ArcFace, buffalo_l) на сервері, Python | Один раз на сесію, CPU достатньо (~50 мс/обличчя) |
| Liveness | Активна: повороти голови, моргання (MediaPipe blendshapes). Пасивна: пізніше | Проти фото на екрані телефона |
| OCR документа (fallback) | PaddleOCR (підтримує кирилицю) або Tesseract + ukr | Якість фото з вебкамери низька → часто ручна перевірка |
| Анти-підміна під час іспиту | Face match кожні 2-5 хв проти еталона (embedding на клієнті через невелику модель або снапшот на сервер) | Поріг косинусної відстані калібрується на пілоті |

**Проблеми:** близнюки, сильна зміна зовнішності, хіджаб/окуляри, фото в документі 5-річної давності. Рішення: завжди є ручний шлях через проктора.

### 5.2 Погляд і положення голови (ядро ідеї)

**Стек:** MediaPipe Face Landmarker (Tasks API, Web). Дає:
- 478 3D-landmarks, включно з ірисом (індекси 468-477),
- `facialTransformationMatrixes` → yaw/pitch/roll голови,
- blendshapes `eyeLookOutLeft`, `eyeLookInRight`, `eyeLookUp*`, `eyeLookDown*`, `eyeBlink*`.

Важливо: Google прямо каже, що iris tracking **не визначає, куди людина дивиться**. Gaze треба виводити з комбінації: положення іриса в орбіті + поза голови + персональне калібрування (9 точок → лінійна/поліноміальна регресія або маленька MLP, що тренується в браузері за 10 сек).

**Алгоритм детекції "дивиться в кут":**
1. Кожні 100 мс: вектор погляду (yaw, pitch) після калібрування → проєкція у координати екрана. Поза межами екрана = off-screen fixation з напрямком.
2. Фільтр: Kalman / ковзне медіанне вікно (прибрати тремтіння). Ігноруємо фіксації < 400 мс (саккади, моргання).
3. Накопичуємо off-screen fixations за ковзне вікно 5 хв.
4. **DBSCAN** на напрямках (yaw, pitch): якщо є кластер з ≥ N фіксацій і сумарним dwell ≥ T секунд → "повторювані погляди в одну зону" (сильний сигнал). Розсіяні погляди в різні боки → слабкий сигнал (людина думає).
5. Кореляція з іншими подіями: погляд у зону → через 2-5 сек ввід відповіді (патерн "подивився-записав") підсилює; погляд у зону під час читання довгого питання послаблює.
6. Вихід: не "списує", а подія `GAZE_CLUSTER{direction, dwell, count, confidence}` з кліпом.

**Пороги задаються політикою ЗВО** (м'яка / середня / сувора) і калібруються на пілотних даних з розміткою прокторів.

**Відомі проблеми:**
- Окуляри з відблисками → іриси не детектяться → fallback тільки на позу голови (гібридна схема, як у дослідженнях Manipal).
- Два монітори: другий монітор виглядає як off-screen кластер. Тому перевірка одного монітора до іспиту.
- Студент з папером і ручкою (дозволено на багатьох іспитах!) дивиться вниз постійно. → політика іспиту має поле "дозволені чернетки", що приглушує сигнал "погляд вниз".
- Точність 4° при найкращих умовах означає, що ми **не** відрізнимо "дивиться на телефон біля клавіатури" від "дивиться на клавіатуру". Чесно це визнати в UI проктора: показуємо кліп, не стверджуємо факт.

### 5.3 Інші сигнали (без них gaze марний)

| Сигнал | Як | Вага |
|---|---|---|
| Обличчя відсутнє > 10 сек | MediaPipe face count = 0 | Висока |
| Два+ обличчя | face count ≥ 2 | Висока |
| Інша людина (face match провалено) | embedding mismatch | Критична |
| Телефон / книга в кадрі | YOLOv8n (COCO: cell phone, book, laptop) on-device 1 fps + серверна перевірка кліпу важчою моделлю | Середня (багато FP на пульти, пляшки) |
| Губи рухаються + голос (без аудіо-запису) | blendshapes `jawOpen`, `mouthFunnel` + VAD | Середня |
| Вихід з fullscreen / втрата фокусу / зміна вкладки | `visibilitychange`, `blur`, `fullscreenchange` | Середня-висока (але Moodle у тій же вкладці, акуратно) |
| Copy/paste великих обсягів тексту | `paste` event, довжина | Середня |
| Другий монітор | `getScreenDetails`, `screen.isExtended` | Висока до старту |
| Віртуальна камера / VM | label пристрою, WebGL renderer string (VMware, VirtualBox), відсутність GPU | Середня (евристики обходяться) |
| Аномальна швидкість відповідей | з Moodle: час на питання vs складність | Середня, потребує інтеграції з логами Moodle |
| Розміри вікна / DevTools | resize + `console` timing trick | Низька |

**Скоринг:** зважена сума з decay у часі + правила ("критична подія → одразу у топ списку"). У МВП: прості правила і ваги в конфігу. Пізніше: логістична регресія / gradient boosting на розмічених даних прокторів. **Ніколи не чорна скринька:** проктор бачить, які сигнали дали бали.

### 5.4 Запис і сховище

- `MediaRecorder` → WebM/VP9 (Chrome, Edge, Firefox), H.264/MP4 у Safari (Safari = головний біль, окреме тестування).
- Чанки по 10 сек → IndexedDB → upload через presigned URL (S3 multipart). При розриві мережі чанки чекають локально (ліміт ~500 MB квоти браузера → 90 хв при 400 kbps ≈ 270 MB, влазить).
- Серверна склейка (ffmpeg concat) після іспиту, генерація кліпів навколо подій, thumbnail-стріп для таймлайну.
- **Хеш кожного чанка** (SHA-256) записується одразу у БД → незмінність доказів для апеляцій.
- Lifecycle: відео без флагів видаляється через 14-30 днів; з флагами зберігається до закриття апеляційного періоду (визначає ЗВО, типово 1 семестр). Ембеддинги обличчя видаляються після семестру.
- Шифрування at rest (SSE-S3 або client-side з ключем ЗВО), TLS in transit.

### 5.5 Інтеграція з Moodle

- **LTI 1.3 Advantage** (Tool Provider): запуск з курсу, NRPS (список студентів), AGS (повертаємо "статус прокторингу" як оцінку/позначку).
- Для паузи таймера і логів відповідей потрібен **Moodle Web Services** токен від адміна ЗВО або **власний Moodle plugin** (quizaccess rule, PHP) — як у Safe Exam Browser. Плагін типу `quizaccess_nocheating`: не дає почати тест без активної сесії прокторингу. Це Фаза 2.
- Альтернатива швидкого старту: наш клієнт відкриває Moodle у `iframe` всередині нашої fullscreen-сторінки. Проблема: `X-Frame-Options` у Moodle часто забороняє. Потрібне налаштування з боку ЗВО.

### 5.6 Мобільний компаньон (телефон)

- **PWA**, не нативний застосунок у МВП (немає стор-ревью, одна кодова база).
- Пейрінг QR-кодом → WebRTC через SFU (LiveKit self-hosted або mediasoup) або просто MediaRecorder + upload так само, як десктоп.
- Функції: (а) друга камера збоку на весь іспит; (б) room scan за політикою; (в) запасний канал, якщо вебкамера ноута зламана.
- Проблеми: телефон розряджається за 90 хв зі ввімкненою камерою; екран гасне (Wake Lock API); iOS Safari PWA обмеження на фонову камеру. Треба UX "поставте на зарядку".

### 5.7 Кабінет проктора

- React + таймлайн-компонент (vis-timeline або власний на canvas), відеоплеєр з перемоткою на маркери (hls.js або звичайний `<video>` з byte-range).
- Live-режим (бачити 20 студентів сіткою в реальному часі) — **Фаза 3**, бо потребує SFU і зовсім іншої інфраструктури. Для МВП: асинхронний перегляд після іспиту + realtime лише стрічка подій (WebSocket).

## 7. Потужності та вартість (оцінка для пілоту: 1 ЗВО, 2000 студентів, пік 300 одночасно)

### Трафік і сховище
- 1 студент × 90 хв × 400 kbps ≈ **270 MB**.
- 300 одночасно → **~120 Mbps** вхідного трафіку (норма для будь-якого VPS/хмари).
- Один іспит на 300 студентів → **~80 GB**. 50 іспитів/семестр → **4 TB** без lifecycle; з видаленням "чистих" через 14 днів реально зберігається ~0.5-1 TB.
- Вартість S3-подібного сховища: ~$5-25/TB/міс → **$10-50/міс** на пілоті.

### Обчислення
- API + БД + черга: 2-4 vCPU, 8 GB RAM → **$20-40/міс**.
- ML-воркери (post-hoc): face match CPU миттєво; перевірка флагів YOLOv8m на GPU T4 ≈ 300-500 fps → 300 студентів × 10 хв підозрілих фрагментів × 2 fps = 360k кадрів ≈ **15-20 хвилин GPU** на іспит. Оренда GPU on-demand ~$0.5-1/год → копійки. Або CPU-only вночі.
- Live-прокторинг (Фаза 3): SFU LiveKit, 300 потоків 400 kbps → ~120 Mbps, 4-8 vCPU → **+$50-100/міс**.

**Разом пілот: ~$100-200/міс інфраструктури.** Основна вартість — люди, не сервери. Це наслідок edge-first архітектури.

### Ліміти на клієнті
- MediaPipe Face Landmarker: ~20-30 fps на Intel i5 8-го покоління / M1; ~8-12 fps на Celeron N4020 (типовий дешевий ноут студента). Треба бенчмарк і адаптивний fps.
- Пам'ять: MediaPipe WASM ~100-150 MB, ONNX YOLOv8n ~50 MB, IndexedDB буфер до 300 MB. На 4 GB ноуті з Chrome — впритул. Firefox/Safari гірше.
- Мобільний інтернет 3G (село, блекаут, роздача з телефона): 400 kbps upload може не триматись → адаптивний бітрейт (знижуємо до 150 kbps і 5 fps).

## 8. Правове поле (не обійти, визначає продукт)

### Україна
- **Чинний:** ЗУ "Про захист персональних даних" №2297-VI (2011). Біометрія явно не виділена як спецкатегорія, але обробка даних про здоров'я/особливі дані вимагає згоди.
- **Прийдешній:** законопроєкт **№8153** (нова редакція, GDPR-подібна) прийнятий у першому читанні 20.11.2024, станом на кінець 2025 готується до другого читання. Вводить визначення **біометричних даних** (оцифроване обличчя), обов'язкового DPO, великих штрафів, DPIA. **Проєктувати одразу під 8153/GDPR**, бо він буде чинним до того, як продукт вийде на ринок.
- Студенти за кордоном (їх багато) → **GDPR застосовується** напряму, якщо ЗВО обробляє дані резидентів ЄС.
- Освітнє регулювання: МОН не має єдиної норми про прокторинг; кожен ЗВО затверджує своє "Положення про дистанційний контроль знань". Продукт має давати ЗВО **шаблон положення і згоди**.

### Що з цього випливає для дизайну
1. **Згода студента в умовах нерівності влади (студент vs університет) є юридично сумнівною** за GDPR. Тому ЗВО **зобов'язаний давати альтернативу** (очний іспит, іспит у Zoom з живим проктором). Продукт має цю альтернативу передбачати в UI ("Я не погоджуюсь → контакт деканату").
2. **Мінімізація:** за замовчуванням не записуємо аудіо, не скануємо кімнату, видаляємо чисті записи швидко, ембеддинги не передаємо третім сторонам.
3. **DPIA** (оцінка впливу) — підготувати шаблон для ЗВО. Ми як процесор, ЗВО як контролер. Договір про обробку (DPA).
4. **Прозорість алгоритму:** студент має право знати, за якими критеріями його оцінюють. Публічний документ "Які сигнали ми фіксуємо".
5. **Жодних автоматичних рішень** з юридичними наслідками (ст. 22 GDPR, аналог у 8153). Рішення завжди приймає людина.
6. **Data residency:** ЗВО, особливо державні, можуть вимагати зберігання в Україні. Закласти вибір регіону сховища.
7. **Прецеденти:** Ogletree v. Cleveland State (room scan = порушення 4-ї поправки, США); скарги на Proctorio в Нідерландах і Німеччині за GDPR. Усі конкуренти, що покладались на агресивне спостереження, отримали репутаційні втрати.

## 9. Ризики і проблеми (повний список)

### Технічні
| Проблема | Серйозність | Мітигація |
|---|---|---|
| Блекаути і втрата зв'язку посеред іспиту (специфіка України) | Критична | Локальний буфер, автореконект, "період без спостереження" як нейтральний стан, кнопка паузи для тривоги, sync з таймером Moodle |
| Слабкі ноутбуки студентів | Висока | Пре-тест бенчмарк, адаптивний fps, серверний fallback, мінімальні вимоги публічно |
| Safari / iOS | Висока | Окреме тестування; у МВП офіційно підтримуємо Chrome/Edge/Firefox, Safari "best effort" |
| Дешеві вебкамери 480p, контрове світло | Висока | Пре-тест якості кадру, підказки студенту (світло спереду), поріг якості, при якому gaze вимикається і лишається тільки поза голови |
| Окуляри, відблиски, косоокість, ністагм, птоз | Висока (і етична) | Hybrid fallback; поле "особливі потреби" у профілі студента, що вимикає gaze-сигнали; завжди людина вирішує |
| Обхід: віртуальна камера з прекордом, другий пристрій поза кадром, навушник, людина поза кадром, що підказує через чат | Висока | Евристики проти вірт. камер; друга камера з телефона (сильно ускладнює обхід); аудіо-VAD; періодичні "живі" челенджі (повернути голову за запитом). Чесно: **100% захисту немає**; мета — підняти вартість списування і дати докази |
| Deepfake / реалтайм face swap | Середня (зростає) | Liveness-челенджі, аналіз артефактів на сервері, друга камера |
| Витік відеоархіву | Критична (репутаційно летальна) | Шифрування, короткий retention, RBAC, аудит-лог доступів прокторів, пентест перед прод |
| Хибні спрацювання переповнюють проктора | Висока | Калібрування порогів на пілоті, feedback loop, UI пріоритизації |

### Етичні та соціальні
- Студенти сприймають прокторинг як недовіру і стеження. Опір, петиції, пости в соцмережах. → Прозорість, мінімізація, залучення студради до дизайну згоди, публічний "що ми не робимо".
- Bias: моделі детекції облич історично гірше працюють на темній шкірі та при нестандартних рисах. MediaPipe зараз непоганий, але **треба тестувати на різноманітній вибірці** і документувати.
- Нейровідмінні студенти (ADHD, аутизм): рухливість, уникання погляду на екран → хибні флаги. → Профіль особливих потреб, інклюзивна політика.
- Студенти в укриттях, спільних кімнатах, з дітьми: "друга людина в кадрі" не є списуванням. → Проктор бачить контекст, а не вердикт.

### Бізнесові
- Українські ЗВО бідні; держзакупівлі через Prozorro; довгі цикли продажу (семестр). → Freemium для одного факультету, гранти (USAID/EU digital education), партнерство з МОН/Дія.Освіта.
- Конкуренти: Proctorio, Honorlock, Respondus (дорогі, англомовні, не інтегровані з Дією). Російські Examus/ProctorEdu — неприйнятні для українського ринку з очевидних причин. **Ніша "український, з Дією, під наші блекаути і закон 8153" реально порожня.**
- Команда: мінімум 1 фронт (ML-in-browser), 1 бек, 0.5 ML/Python, 0.5 дизайнер/UX-рисерч, юрист на консультації. 3-4 людини на МВП.

## 10. Роадмап

### Фаза 0 — Discovery (2-4 тижні, без коду або з прототипами)
- 5-10 інтерв'ю з викладачами і 10-20 зі студентами (що болить, що не толерується).
- 1-2 ЗВО-партнери для пілоту (letter of intent).
- Юридична консультація: 8153, згода, DPIA-шаблон.
- Технічний spike (одноразові прототипи, викинути):
  - MediaPipe Face Landmarker у браузері → yaw/pitch + iris ratio → калібрування → heatmap. Перевірити точність на 5 людях з різними камерами.
  - MediaRecorder chunked upload з розривом мережі.
  - Дія: подати заявку на тестовий токен (бюрократія йде паралельно).

### Фаза 1 — МВП (8-12 тижнів)
Мета: один пілотний іспит на 30-100 студентів в одному ЗВО.
- Монорепо (pnpm workspaces або Turborepo): `apps/web` (студент + проктор), `apps/api`, `services/ml`, `packages/shared`.
- Студент: згода, перевірка пристрою, еталон обличчя, калібрування, запис + події, chunked upload, буфер, пауза.
- Сигнали: обличчя 0/2+, face mismatch, погляд off-screen з кластеризацією, поза голови, фокус/вкладки/fullscreen, другий монітор.
- Проктор: список, таймлайн, кліпи, рішення, експорт PDF.
- Інтеграція Moodle: LTI 1.3 launch (без паузи таймера).
- Інфра: Docker Compose на одному сервері, MinIO, PostgreSQL, Grafana.
- Без: room scan, телефон, аудіо, live-режим, Дія (якщо токен ще не отримано — OCR fallback).

### Фаза 2 — Пілот і калібрування (6-8 тижнів)
- 3-5 реальних іспитів, розмітка прокторами, збір FP/FN, налаштування порогів.
- Дія.Шеринг прод.
- Телефон як друга камера (PWA, WebRTC або upload).
- Moodle plugin `quizaccess` + пауза таймера.
- Профіль особливих потреб, аудит-лог, DPA/DPIA документи.
- Пентест.

### Фаза 3 — Масштаб (далі)
- Live-режим (SFU), чат проктор↔студент.
- ML-скоринг на розмічених даних замість ручних ваг.
- Multi-tenant, біллінг, Prozorro-готовність.
- Room scan як опція (тільки якщо ЗВО наполягають і юристи ок).
- Інтеграції: Google Classroom, Canvas, власний тестовий модуль.

## 11. Метрики успіху пілоту
- Технічні: ≥ 95% сесій завершені без втрати запису; p95 завантаження клієнта < 10 сек; частка пристроїв, що не пройшли бенчмарк < 10%.
- Якість детекції: precision топ-10% за рівнем підозри ≥ 60% (підтверджено проктором); recall на "підсадних" тестових порушеннях ≥ 80%.
- Проктор: час перегляду групи 100 студентів ≤ 60 хв.
- Студенти: NPS не нижче -20 (прокторинг ніхто не любить, але не має бути ненависті); < 5% відмов від згоди.
- Юридичне: 0 інцидентів з даними; DPIA затверджено ЗВО.

## 12. Відкриті рішення (мої дефолти, якщо не заперечиш)

1. **Формат постачання:** B2B SaaS + Moodle LTI (дефолт) vs standalone з власними тестами. → Дефолт: Moodle-first.
2. **Перший клієнт:** конкретний ЗВО вже є? Без нього Фаза 0 починається з пошуку партнера.
3. **Room scan у МВП:** ні (дефолт) через юридичні ризики і репутацію.
4. **Аудіо:** тільки VAD без запису (дефолт).
5. **Data residency:** Україна (дефолт) чи ЄС (Hetzner дешевше і стабільніше). Можна зробити вибір per-tenant.
6. **Мова бекенду:** TypeScript (NestJS) для API + Python для ML (дефолт) чи все на Python.
7. **Статус проєкту:** навчальний/дипломний, стартап, грант? Впливає на глибину юридичної частини і на те, чи взагалі робити Дію (потрібна юрособа).
8. **Що саме починати будувати першим**, якщо затвердиш план: технічний spike з Фази 0 (gaze-прототип у браузері + chunked recorder) у цьому репозиторії.
